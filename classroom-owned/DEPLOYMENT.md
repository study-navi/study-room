# 公開候補と承認範囲

この手順書は運営側の設定用。各教室の先生はGAS・SQL・APIキーを操作しない。以下の外部設定・公開・実データの変更はまだ行っていない。

## 今回提案する検証環境

- Google Cloud：Study Room専用のOAuthクライアントと同意画面。Google Drive API・Sheets API。ログイン権限はopenid・email・drive.fileに限定。請求先の追加や割当増額を行わない。
- Cloudflare：Workers Freeプラン。Worker名`study-room-classroom-owned-staging`、SQLite Durable Objectクラス`StudyRoomRegistry`、非公開名前空間REGISTRY。R2・D1・KV・有料プランは追加しない。
- 公開するもの：ログイン／登録画面、教室別の生徒画面、取り扱い案内。保存先、認証情報、学習記録を一般公開しない。
- Cloudflareで扱うもの：教室と先生の対応、ログイン状態、暗号化した継続認証情報、送信途中の学習記録。Googleに保存が確認された途中記録は削除する。処理場所は日本国内に限定されない。
- 検証対象：承認を受けた先生2アカウントと架空の生徒・記録だけ。先生のDriveに各教室の専用Sheetsと非公開バックアップを作る。
- 影響しないもの：既存GitHub PagesのURL・GAS・元スプレッドシート・現行記録。切替や移行をこの承認へ含めない。

Cloudflare Freeには日次の要求数・SQL読書き等の上限がある。初期構成は有料プランへの切替・有料オプションの有効化を含めない。無料上限を超えた場合はエラーとして対応し、勝手に課金・上限引上げを行わない。Google側の現行の割当と料金条件も実設定時に確認する。

## 検証用環境での実Google確認結果（2026-10-22〜23）

- 確認済み（架空データ）：実Googleログイン、専用Sheets作成、生徒の入退室と振り返り送信、教室モード、記録修正、ソフト削除（deletedAtが付き行は残る）、検索、手動バックアップ（取得時点の内容）、CSVの内容。
- 確認済み：通信遮断時の送信失敗・リロード復元・再送（二重登録なし）、Google権限の取り消し後の再ログインと既存教室の継続。
- 確認済み：別Googleアカウント2つで、一覧の分離と、互いの管理画面への直接アクセス拒否。
- 利用者の報告：スマホでのPWA（ホーム画面追加、機内モードで起動）。
- 未確認：翌日の日次バックアップ。バックアップからのアプリ内復元は機能がなく、手作業になる。
- Workers固有の注意：fetchのredirect:errorは未実装のためmanualを使う。fetchをオブジェクトのメソッドとして呼ぶとIllegal invocationになる。worker-check.mjsに回帰検証がある。
- Google OAuthのTesting状態ではリフレッシュトークンが失効するため、他教室向けには公開状態（本番環境）が必要。openid・email・drive.fileは機密性の低いスコープで、検証センターでも検証不要と表示された。
- 本番用Workerは別名`study-room-classroom-owned`（`--env production`）とし、別のDurable Object名前空間・別のSR_KEYを使う。検証用の架空データは持ち込まない。


## 承認後の設定順序

1. Cloudflareの対象アカウントとFreeプランを確認。新規アカウントで規約同意が必要なら利用者本人が行う。
2. 検証Workerを作成して実URLを取得する。認証用設定が不足した間は503で停止する。検証用公開だけで旧サイトは切り替わらない。
3. Google Cloudで専用プロジェクトとOAuth Webクライアントを設定。対象URLを確定してから正確なリダイレクトURIを`https://<検証ホスト>/auth/callback`に登録。任意リダイレクトを許可しない。
4. 同意画面のサポート窓口、アプリURL、`/privacy`、承認済みの検証アカウントを設定。Testing状態の更新トークンは期限の制約があるため、その状態で他教室の長期運用を開始しない。
5. 次の設定をCloudflareの非公開設定・Secretへ保存。SecretをGitHub、画面、URL、チャット、ログに書かない。

| 設定 | 値／扱い |
| --- | --- |
| `SR_ORIGIN` | 検証Workerの正確なHTTPS origin（末尾スラッシュ・パスなし） |
| `GOOGLE_CLIENT_ID` | 専用OAuthクライアントID |
| `GOOGLE_CLIENT_SECRET` | Googleで発行されたclient secret、非公開 |
| `SR_KEY` | 暗号学的乱数32バイトをbase64化した暗号鍵、Secret。DBと別の安全な場所に復旧用控えを保存 |
| `SR_CONTACT_EMAIL` | 実際の運営窓口。公開することを確認したアドレス |

6. Secret投入前後にキーやトークンを表示しない。暗号鍵を失うと継続接続情報を復号できない。無断で再生成・差替えをしない。
7. 実環境で次の受入確認を完了する。

## 実環境の受入確認（未実施）

- 先生Aと先生Bが別々のGoogleでログインし、専用Sheetsが各自のDriveに所有されている。
- 先生Aが先生Bの教室IDを使っても一覧・編集・削除・QR・バックアップへアクセスできない。
- シート／バックアップが非公開で、一般公開や他人への共有権限が追加されていない。
- 生徒の別ブラウザからログインなしで入室・休憩・退室・振り返り・履歴が動く。同姓同名でも本人の端末キーがない履歴を取得できない。
- 通信遮断と再送・リロード・未送信記録の復元。記録件数と実利用人数の集計が一致する。
- 先生の検索・編集・論理削除・ランキング・CSV・教室モード・在籍数／利用率・本人確認後の引継ぎ。
- QRを実スマホのカメラで読み取り、正しい教室へ入る。教室別にPWAをインストールして教室URLを保持する。
- Googleの継続接続許可を取り消すと送受信が停止し、再接続で既存ファイルのまま復帰する。
- 日次／手動バックアップが正しい所有者・内容で作成され、架空記録を別の検証用コピーで復元して項目・件数を照合できる。
- GoogleとCloudflareの使用量、エラー、運営窓口、公開する取り扱い案内を確認する。

## 本番公開は別の承認後

`wrangler.jsonc`のproduction環境は`study-room-classroom-owned`と別のDurable Object名前空間を使う。検証用DB・トークン・架空記録を本番へコピーしない。Google OAuthの公開状態・ドメイン・窓口を確定し、必要な審査を終えてから本番利用へ切り替える。

本番モードでは窓口設定がなければ503で停止する。公開URLの案内先や旧サイトからのリンク追加も、本番承認の対象とする。

既存4件等の実記録を移行する場合は、最新スナップショットと非公開バックアップを取り、教室・生徒ID対応を先生が確認し、移行先・件数・項目を説明して別途承認を得る。旧ファイルを変更せずコピーし、日時・時間・内容・振り返り・ランキング・CSVを照合する。

## Nodeで運用する場合

同じコードをNode 24の永続ディスク付きホストで起動できる。`npm ci --omit=dev`、`npm run build`の後、`SR_ORIGIN`、`GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`、`SR_KEY`、`SR_DATABASE`（非公開の永続パス）を設定して`npm start`。TLS終端を同一originで構成し、内部の127.0.0.1:8080へ転送する。

この方式は既存の常時稼働ホストがある場合の代替であり、無料ホストの一時ディスクへSQLiteを配置しない。Google API・ローカルSQL・暗号鍵をバックアップする。アクセスログに認証コールバックのクエリやPOST本文を記録しない。通信不明・スキーマ競合時に未完了データを削除して回避しない。
